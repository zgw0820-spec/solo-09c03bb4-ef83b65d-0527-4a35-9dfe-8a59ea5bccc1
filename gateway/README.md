# 冷库网关：采集进程热换版 + 记录仪双入口就绪竞速

冷库温度记录仪通过 **一条 TCP 长连接** 持续上发逐行 JSON 读数。网关侧有两项能力：

**A. 采集进程热换版（v1 → v2）**

- 记录仪只连接一次，换版期间 TCP 连接不中断、不重连；
- 旧进程处理完手头已收到的完整读数后，把连接交给新进程；
- 已发出但尚未处理的读数沿原连接按发送顺序继续收，每条只确认一次；
- 新版启动失败时自动回退，旧进程继续收数；
- FastAPI 操作页展示每笔确认的读数编号与处理进程版本。

**B. 双入口模式（模拟记录仪）**

记录仪开机时主入口可能已能建连，但采集端尚未准备好。双入口模式：

1. **先连主入口**，等待采集端在连接上回写一行就绪答复 `{"type":"ready",...}`，收到才开传；
2. **主入口明确失败**（建连被拒、或就绪前连接被对端关闭）→ **立即试备用**；
3. **主入口在 `failover_after` 秒内还没就绪** → 也启动备用尝试，**同时继续等主入口**；
4. 在**总等待时限 `total_timeout`** 内，**最先返回就绪答复的那一路胜出**；
5. 整批读数**只走这条 TCP 连接**；选定后**立即中止另一路尝试并关闭其连接**，迟到的答复**不可能再触发发送**（读线程已退出、fd 已关闭）；
6. 到期仍无一路就绪 → **本批不发**（记录仪退出码 3，操作台显示“本批未发”）；
7. **兼容现有单入口记录仪**：`--mode single`（默认）行为与以前完全一致——建连即发，不读回执；采集端写出的就绪行对它是无害的多余字节。

## 工作原理

```
                ┌──────────────────── gateway 容器 / 单 supervisor 进程 ───────────────────┐
  记录仪(客户端) │  主入口 TCP:9000 ── accept ──┐                                           │
  先连主入口     │  备用入口 TCP:9001 ── accept ─┤                                           │
  等就绪答复     │                              │ SCM_RIGHTS 传连接 fd（SEQPACKET 控制通道）  │
  再整批发送     │                              ▼                                           │
                │              ┌──────────────────────┐        ┌──────────────────────┐     │
                │              │ 采集进程 v1（子进程）  │ 换版   │ 采集进程 v2（子进程）  │     │
                │              │ 持有记录仪 TCP fd      │ ─────▶ │ 接手同一个 TCP fd      │     │
                │              └──────────────────────┘        └──────────────────────┘     │
                │                        ▲  启动失败：v2 退出，v1 继续收数（自动回退）           │
                │              FastAPI 操作页 :8000（记录仪双入口竞速 / 入口延迟 / 换版 / 校验） │
                └──────────────────────────────────────────────────────────────────────────┘
```

关键机制：

1. **监听 socket 归 supervisor 所有**，采集进程是独立子进程（独立版本号、独立 pid），
   自身不 accept 连接。supervisor accept 后通过 Unix 域套接字 + `SCM_RIGHTS`
   把 TCP 连接 fd 发给当前采集进程。**主/备用是两个独立监听端口**（9000 / 9001），
   记录仪的竞速是真实的网络层选择。
2. **换版即 fd 交接**，不是断连重连。内核里同一个 `struct file`（同一四元组、
   同一接收缓冲区）被复制到新进程，记录仪完全无感知。
3. 控制通道选用 **`SOCK_SEQPACKET`**：既面向连接、可靠，又保留消息边界，
   保证一次 `recvmsg` 同时取到整帧和附属 fd（STREAM 上先读长度头会吞掉
   SCM_RIGHTS 辅助数据，这是本项目实现中实测踩过的坑）。
4. **半行不丢不重**：旧进程换版时先把缓冲区与内核中已到达的**完整行**全部处理，
   剩余的不完整半行（leftover）随 fd 一起交给新进程；新进程先拼完半行再继续读。
5. **逐条确认、仅一次**：每个读数 id 的确认事件按连接记录，服务端实时检测重复确认；
   `/api/verify` 独立校验编号 1..N 连续、无重复、版本分界为干净的前缀/后缀，
   并**按入口汇总**采集端确认过的读数编号。
6. **启动失败回退**：换版先拉起新版本并等待 `ready`；失败标记文件存在时新版本
   启动即失败，supervisor 不发起交接，旧进程与原连接原封不动继续工作。
7. **就绪延迟按入口、按连接生效**：`new_conn` 控制帧带上入口名与延迟秒数，
   采集进程为每条连接记录一个绝对就绪时刻，到点在**该连接上**写一行就绪 JSON。
   延迟随 fd 交接一起传递（绝对时刻），换版不会重启延迟计时；已发过就绪答复
   的连接在交接后不会重复发。
8. **入口故障模拟**：把某入口标为 `fail` 后，supervisor accept 该入口的连接、
   记录事件、随即关闭——记录仪看到“就绪前 EOF”，按“明确失败”立即切备用。

读数行格式（`\n` 结尾的 JSON）：

```json
{"id": 7, "sensor": "freezer-1", "temp_c": -18.4, "ts": 1731000000.123}
```

就绪答复行（采集进程 → 记录仪，`\n` 结尾的 JSON，记录仪读取并忽略其它字节）：

```json
{"type": "ready", "entry": "primary", "collector": "v1", "peer": "10.0.0.5:41000", "ts": 1731000000.5}
```

## 目录结构

```
gateway/
├── app/
│   ├── main.py         # 入口：supervisor + uvicorn/FastAPI
│   ├── supervisor.py   # 双入口监听、进程编排、换版/回退、fd 中继、事件与校验
│   ├── collector.py    # 采集进程：读数解析、逐条确认、入口就绪答复、交接
│   ├── recorder.py     # 模拟记录仪：单入口（兼容）/ 双入口就绪竞速

│   ├── webapp.py       # FastAPI 路由
│   └── web/            # 操作页（index.html / app.js）

├── Dockerfile
├── docker-compose.yml
└── requirements.txt
```

## 用 Docker Compose 启动

```bash
cd gateway
docker compose up --build
# 操作页：  http://localhost:8000/
# 主入口：  localhost:9000
# 备用入口：localhost:9001
```

页面操作（也全部有对应 REST API）：

1. **① 模拟记录仪**：选择入口模式（默认双入口）、总等待时限、总数/间隔/暂停点，
   以及“主入口迟迟未就绪多久后也尝试备用”，点击“启动记录仪”。
2. **①b 入口就绪策略**：分别为主入口、备用入口设置**就绪延迟（秒）**，可勾选
   “模拟明确失败”。用于演示主入口迟答、备用抢先、两边都超时。
3. **② 换版**：暂停窗口内输入新版本号 `v2`，点“执行换版 / 交接”。
   勾选“模拟新版启动失败”可演练回退；也可手动放置失败标记。
4. **⑦ 各路尝试结果**：按入口展示状态（connecting/connected/ready/ready_late/
   failed/aborted/timeout）、阶段、建连与就绪耗时、胜出入口，以及“本批未发”提示。
5. **④ 逐笔确认** 表格实时显示每笔读数编号、**入口**、处理进程版本、温度、连接、确认序号。
6. **⑤ 校验结果** 显示编号连续性、唯一性、各版本处理的编号区间，以及**按入口**
   汇总的采集端确认编号。

也可以用 compose 里的独立记录仪容器（同一镜像，recorder profile）：

```bash
# 双入口竞速
docker compose --profile recorder run --rm recorder \
  python -m app.recorder --mode dual --host gateway --port 9000 \
  --backup-port 9001 --count 60 --failover-after 1 --total-timeout 8

# 兼容旧单入口
docker compose --profile recorder run --rm recorder \
  python -m app.recorder --mode single --host gateway --port 9000 --count 60 --gap-at 20
```

## REST API 摘要

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET  | `/api/status` | 版本、进程、双入口配置与端口、记录仪竞速结果、重复确认 |
| GET  | `/api/events?cursor=N` | 增量事件流（确认、换版、入口就绪/失败、竞速报告…） |
| GET  | `/api/verify` | 编号连续性/唯一性/版本分界 + **按入口核对** |
| GET  | `/api/entries` | 两个入口的端口、就绪延迟、故障标记 |
| POST | `/api/entries/{entry}` | `{"delay":3.0,"fail":false}` 设置某入口就绪延迟/故障 |
| POST | `/api/upgrade` | `{"new_version":"v2","simulate_fail":false}` |
| POST | `/api/recorder/start` | `{"mode":"dual","count":60,"interval":0.2,"gap_at":20,"gap_seconds":5,"failover_after":2,"total_timeout":10}` |
| POST | `/api/recorder/stop` | 停止模拟记录仪 |
| POST | `/api/fail-marker` | `{"present":true}` 手动放置/清除启动失败标记 |
| POST | `/api/events/reset` | 清空事件与确认记录 |

## 设计取舍与边界

- 采集进程与 supervisor 放在**同一容器**内：fd 交接依赖同一内核网络命名空间
  与 Unix 套接字，跨容器需要共享 pid/network namespace，复杂度更高且无收益。
- 换版进行中到达的新 TCP 连接会在监听 backlog 中短暂等待，继任者就绪后再投递，
  不会交给即将退出的旧进程。
- 若**活动采集进程异常崩溃**（非换版场景），其持有的连接 fd 随进程释放，
  记录仪会收到 EOF；supervisor 会自动重启同版本进程。换版路径本身不会断连。
- 失败标记是演示“新版启动失败”的模拟手段（文件存在即启动失败），真实系统中
  对应健康检查/版本初始化失败。
- 双入口的**就绪判定是“采集端在该连接上写出了答复行”**；落败连接被关闭后，
  即便采集端随后才到点写出答复，也只会得到 EPIPE，记录仪侧无读者、无发送。
- 主入口“明确失败”包括：建连失败、就绪前 EOF；**仅被延迟**不算失败，
  此时按 `failover_after` 并行启动备用、并继续等主入口。
- 若 `failover_after` 很大而主入口延迟很短，则备用可能根本不会被尝试
  （这正是“主入口迟答”场景的预期行为，操作台会显示“未尝试”）。
